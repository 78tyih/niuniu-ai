01需求重构：把三件事拆开

原设定把三件事串成一条链，导致任一环都要求伙伴配合。拆开后，伙伴只参与最后一件。

拆开之后，“全自动”的依赖面从“伙伴改源码”降为“伙伴给一把可撤销的批发凭证”。

03上游接口能力（实测更正）

我第一轮 brief 里写过“New API 管理接口只有 Session 鉴权”，这句是错的。官方文档明确支持 Access Token，自动化不需要改源码。

但这不是让你去接裸 Admin 令牌。Public / User / Admin / Root 是角色分级，不等于接口级权限控制 —— 一把 Admin 令牌能改任意用户额度、读其他客户、动系统配置。三个通道一致建议：优先要伙伴提供受限经销商接口或独立租户；只能给 Admin 令牌时，必须专用账号 + 出口 IP 白名单 + 单项与累计限额 + 操作审计 + 可即时撤销。

04分账：请求同步，资金异步

不要在请求链路里实时分账。上游延迟、重复扣款、跨系统不一致会直接传导给客户。

最大的“自动化幻觉”：充值码 ≠ 资金结算。New API 的充值码只是平台内记账动作，它不能证明钱已经付给伙伴。企业间付款要么伙伴给你授信（后付费），要么走对公转账按周批量 —— 后者按定义就不可能是全自动的。三通道都把这个断点单独拎了出来。

05合规红线

我补做了行业调研后加的维度 —— 也是六份答案里最一致的部分。“号池”这个词本身就是红灯。

“我不知道上游怎么拿的货”不是有效抗辩。异常低价、批量账号、拒绝提供来源，都可能被认定为“明知或应知”。反过来，报道里的刑事个案也不能推出“所有分销都违法” —— 具体责任取决于来源、授权、主观明知和参与程度。这一节需要中国律师给意见，不是我能替你下结论的地方。

06实施闸门

两处红色是硬闸门 —— 卡在这里就不要往下写代码。

  • P0 商务前置：批发价与调价通知期、SLA、不绕客条款、预付上限、未用额度退款期、数据用途与留存。谈不拢就不做伙伴专用集成。
  • P4 支付闭环：ZPay / Stripe 回调验签 + 订单幂等 + 到账自动加积分。重放、乱序、延迟回调都不能重复入账。
  • 律师意见前：不应面向境内公众正式收费上线。内部合成数据原型可以先做。
  • 会计意见前：不应启动充值余额、长期预付套餐或代收代付模式。
