• **1. 结论：选 B，但应把它落成“批发额度池 + 本侧客户账本 + 周期净额结算”，不要带每客户上游 token。**

  **理由：**
  - B 保留了客户入口、定价权、计费权、服务数据和替换供应商的能力，也最符合现有 `nk1.*` 令牌及预扣结算体系。
  - A 中，客户可提取上游地址和 token，伙伴又掌握开户、用量和续费入口，最容易被绕开。此时剩余护城河只有 MT5/EA 集成、交易工作流、提示词与工具链、客户端体验、品牌及售后；如果 AI 只是通用聊天，这部分护城河很薄。
  - C 同时承担上游开户复杂度和本侧流量责任，却没有换来对等的客户隐匿或结算优势，现阶段最不划算。
  - 但“每客户一个上游 token”并非绝对无用：只有需要上游强制执行单客户限额、封禁隔离，或伙伴必须提供独立客户账单时才有价值。它不能替代自己的账本，反而增加密钥同步、泄露、销户和个人信息关联问题。

  **具体做法：**
  - 上游只持有少量生产 token，按环境、伙伴或故障域划分，例如 2–4 个，绝不按客户划分。
  - 客户维度只存在于自己的虚拟子账本：内部客户 ID、调用 ID、模型、tokens、客户实扣积分、上游成本、结算状态。
  - 确实有遗漏的第四种交易模式：**预付批发额度池**。客户充值全部是自己的销售收入，伙伴按批发价提供额度，双方按周期对账、补货或付款，不做“每客户充值后实时转一笔给伙伴”。这不是新的流量拓扑，却是比 A/C 更合适的商务模式。
  - 若未来确有单客户上游强隔离需求，再升级 C；不要现在为它预付复杂度。

  ---

  **2. 结论：三条路都不能在“伙伴不配合”的前提下单方面完成；(a) 最适合正式自动化，(b) 不应作为生产方案，(c) 只是补货手段。伙伴不改源码不等于逻辑上只剩 B，但 B 最能绕开这套管理接口。**

  **理由：**
  - (a) 可以由伙伴部署，不要求我控制服务器，但必须由伙伴同意并持续维护。完整 fork 还会带来上游升级、安全补丁和回归测试成本。
  - (b) 需要伙伴交出管理员账号、密码或长期 Session Cookie。New API 管理接口没有细粒度管理 token，拿到的很可能不是“只能开户”的权限，而是整个号池的管理权限。
  - (b) 的具体代价包括：管理员凭据泄露后可操作用户、令牌、充值码和配置；我的服务器成为伙伴整个号池的失陷入口；Session 过期、验证码、2FA、CSRF、页面或服务端流程变化都会导致自动化中断；密码轮换和权限撤销困难；双方操作混在同一个管理员身份下，审计与事故定责困难。
  - (c) 的充值码仍要先生成，生成依然需要管理 Session；客户兑换还需要客户在上游有账户。B 下客户没有上游账户，因此“客户自助兑换”根本不成立。预生成一批码可以摊薄调用，但库存补货仍需人工或另一套自动化。

  **具体做法：**
  - 首选让伙伴做**很小的管理端补丁**，只开放创建用户、创建 token、查询用量等必要端点，并加独立凭据、IP 白名单或 mTLS、限流和审计，不要暴露完整后台。
  - 若伙伴不愿改源码，可让其在**自己服务器上**运行一个受限适配器：管理 Cookie 不离开伙伴环境，只向我的网关暴露少量、带鉴权和幂等键的操作。这仍有模拟 Session 的脆弱性，但比把管理员 Cookie 交给我安全。
  - 若伙伴既不修改也不运行适配器，就取消每客户上游开户，采用 B 的聚合批发模式。
  - 如果“每客户自动开户、每笔资金自动划转、完全零人工”三条都不能调整，而伙伴又不提供任何自动化能力，则不是只剩 B，而是**原始需求整体不可交付**。

  ---

  **3. 结论：调用完成后在本地实时记账，对伙伴按日或按周净额结算；不要在请求链路里同步分账。虚拟子账本不是可选项，而是 B 的核心。**

  **理由：**
  - 实时跨系统分账会遇到“调用已成功但分账失败”“伙伴已入账但本地提交失败”“重试导致重复划拨”等无法靠本地事务解决的问题。没有伙伴侧幂等接口，就不能宣称跨系统精确一次。
  - 它还会把伙伴管理接口的延迟和故障传导到客户请求，并产生大量小额舍入、手续费和对账记录。
  - 周期结算的风险是信用敞口和差错发现较晚，但可通过预付上限、未结额度上限、日报和异常明细控制；对账则从逐笔跨系统匹配，降为周期汇总加异常项处理。
  - A 还有一个额外缺陷：客户直连伙伴后，我的网关看不到调用过程，没有伙伴用量接口或 webhook，就无法可靠地做实时分账。

  **具体做法：**
  - B 正常调用时，每笔只有本来就必须的 **1 次 relay 请求**，New API 在内部扣上游额度；额外的伙伴“分账接口”调用应为 **0 次**。
  - 若硬用兑换码逐笔调平，每个结算单元至少需要“生成充值码 + 兑换”两类调用：逐笔生成就是 2 次，另可能有登录、Session 刷新和用量查询；生成虽可批量摊薄，但仍不建议。
  - 本地保存追加式账务事件：预扣、实扣、退回、上游成本、伙伴应付、结算批次和调整项；使用整数最小单位，不用浮点数。
  - 每日生成按模型、倍率版本、日期聚合的结算单，初期每日核对、每周付款；成熟后再调整周期。
  - 结算单要有唯一批次号和调整入口，重放不能重复付款。跨周期差异走调整单，不修改历史记录。
  - 资金流与调用流解耦：上游额度不足时补的是批发池，不是给某个客户的上游账户充值。

  ---

  **4. 结论：把伙伴跑路、限流和封号视为必然会发生的事件，靠“敞口上限 + 可切换上游 + 客户余额独立核算”保护客户，合同只是补充。**

  **理由：**
  - 合同不能阻止对方失联，也不能保证预付款追回；真正有效的是任何单点失效时，损失金额有限且服务能够切换。
  - 如果把客户充值全部立即换成单一伙伴的不可退 quota，伙伴跑路会同时造成服务中断和客户退款负债。

  **具体做法：**
  - 单一伙伴预付额度限制为滚动 3–7 天预计用量，且不超过公司可承受的全损金额；设置单客户、全局日用量和自动补款上限。
  - 客户余额负债与上游预付资产分开核算，保留退款和服务迁移所需准备，不把“客户还有积分”等同于“伙伴还有额度”。
  - 网关保留统一上游适配层，至少准备第二个可替换伙伴或备用渠道；定义模型映射、价格上限、超时、熔断和保守重试策略，并定期做切换演练。
  - 429、5xx、超时、流中断分别处理；只有确认未交付的调用才释放预扣或退回，不能仅凭客户端超时统一退款。
  - 低余额、限额接近、失败率、上游倍率变化均应提前告警，不能等客户调用失败才发现。
  - 商务前置至少包括：批发价及调价通知期、可用性与限流 SLA、故障响应、封号申诉、未用预付款退款期限、终止过渡期、用量数据导出、保密与不绕客、违约处理。
  - 真发生长期中断且无法替代时，按事先公布的条款提供迁移、服务补偿或未消费余额退款，不承诺无法兑现的永久服务。

  ---

  **5. 结论：B 的聚合账户可以让伙伴看不到客户名单；A/C 无法做到同等效果。“用量混淆”不值得做，商务上应让伙伴靠稳定批发收入获利，而不是靠掌握终端客户。**

  **理由：**
  - A 中伙伴直接开户并看到客户连接，C 中每客户 token 也暴露客户数量和逐客户用量。随机 ID 只是假名化，不能改变伙伴掌握客户关系的事实。
  - 即使采用 B，伙伴及实际模型提供方仍可能看到提示词内容、时间和聚合用量；隐藏名单不等于数据已经匿名。
  - 填充假流量、伪造用量等混淆手段会增加成本、污染对账，甚至可能违反合作约定，保护效果却有限。

  **具体做法：**
  - 技术上只向上游发送必要字段，去除邮箱、授权码、内部客户 ID、设备标识及自定义追踪头；上游 token 命名也不带客户或品牌信息。
  - 客户认证、客户用量和渠道标识全部留在自己网关；伙伴只看到批发账户、网关出口和聚合调用。
  - 对提示词做数据最小化，尤其避免发送不必要的交易账户、姓名和联系方式；与伙伴约定日志保留、是否用于训练、数据再转交及删除机制。
  - 合同加入客户归属、不绕客、不主动营销、不利用用量画像挖客、保密、禁止转售相关数据、终止后删除及合理违约责任，并让保密和不绕客条款在合作终止后继续有效。
  - 商务上给伙伴稳定的批发利润、及时结算和可预期的量级，使其“不需要碰终端客户也划算”。不绕客条款只能兜底，不能替代 B 的技术隔离。

  ---

  **6. 结论：客户侧只保留自己的积分定价；上游分组倍率只作为批发成本参数，不用它再加一次零售毛利。**

  **理由：**
  - 两套体系职责不同：我的积分决定客户付多少，New API 的三级倍率决定我在伙伴处被扣多少 quota。
  - 清晰关系应为：  
    **毛利 = 客户实扣积分 × ¥0.1 − 伙伴批发成本 − 支付及退款等费用。**
  - 如果一边用分组倍率向客户加价，一边又在积分定价里加利润，未必形成技术上的两次扣款，但会形成两张互相嵌套的价格表，极易造成价格不一致和对账争议。
  - 更大的隐患是：当前快问 1 积分、深度 6 积分是按次收费，而上游通常按 token 和倍率计费。长输入、长输出或高倍率模型可能让单次成本超过售价。

  **具体做法：**
  - 自己维护唯一客户价目表，继续执行现有预扣、结算、多退、失败全退。
  - 与伙伴约定独立批发价；若分组倍率 0.8 是批发折扣，就让它降低成本，而不是变成另一套客户售价。
  - 保存每次调用适用的零售价版本、上游倍率版本、quota 换算及汇率/结算币种，禁止伙伴静默改价。
  - 为快问、深度设置模型、最大输入输出和成本上限，持续监控单次最坏成本与毛利率；超限时截断、降级或调整价格，而不是假设固定 1/6 积分永远有利润。
  - 对账只比较两类数：本侧客户实扣总额、伙伴批发用量总额及其成本，不拿两个“加价倍率”互相推算。

  ---

  **7. 结论：最小上线版本应完全避开 New API 管理接口，只做 B 的 relay、自己的账本和周期结算。第 0 步商务门槛谈不拢，就不应开始写伙伴专用自动化代码。**

  **理由：**
  代码无法补上伙伴未提供的管理权限、资金划拨渠道和退款承诺。尤其要防止把“B 不需要逐客开户”误解成“B 自动解决了资金全自动划转”。

  **具体做法：**

  0. **商务与技术前置，先于开发**
     - 谈定：聚合批发模式、批发价和倍率、用量账单、结算周期、预付上限及未用余额退款、SLA、保密与不绕客、终止迁移。
     - 提供测试 relay token、测试额度和样例用量账单。
     - 若坚持原始“每客户自动开户”，必须先增加伙伴部署管理端点或本地适配器的承诺。
     - 若“零人工”还包括周期性批发补款，还必须另有可自动执行的付款/扣款渠道；New API 的兑换码接口并不解决企业间资金支付。
     - **验证：**签署合作及技术附件，测试 token 可调用，双方对一份样例账单的金额计算一致。只接受聚合批发这一步谈不拢，就停止该伙伴的定制开发。

  1. **验收 relay 与账单能力**
     - 验证模型列表、流式响应、tokens/quota 字段、429/5xx、token 吊销和账单导出。
     - **验证：**成功、限流、超时、流中断各跑一组，伙伴账单能对应到测试调用。

  2. **建立客户子账本和成本账本**
     - 将调用 ID、客户 ID、预扣/实扣/退款、上游成本、倍率版本和结算批次贯通。
     - **验证：**模拟重复回调、重试、超时和崩溃恢复，客户余额不少扣、不重扣，账务事件可重放且不重复结算。

  3. **接入 B 的服务端转发**
     - 上游地址和 key 只存在服务端；客户端继续只持有 `nk1.*`，错误信息也不泄露上游地址。
     - **验证：**抓包及检查客户端构建产物、日志和报错，确认没有伙伴 key；无效、吊销和超限额的本侧令牌均被拒绝。

  4. **打通注册、充值、调用全流程**
     - 客户充值只增加本侧积分，不创建上游用户，不触发逐客充值。
     - **验证：**新账户从注册、支付回调、到账、快问/深度调用到余额变化全程自动完成；失败调用按规则退回。

  5. **实现周期对账与结算批次**
     - 自动生成聚合账单、异常明细和调整单；实际自动付款仅接入受支持的支付渠道。
     - **验证：**连续并行核对数日，双方汇总在约定舍入范围内一致；重放结算批次不会重复付款。若只能自动生成结算单而仍需人工付款，应明确标注，不得宣称资金全自动。

  6. **上线保护机制**
     - 加入预付及消费上限、低余额告警、熔断、限流、备用上游和故障退款策略。
     - **验证：**主动模拟伙伴 429、封号、断网及 token 失效，确认不会拖垮网关、不会重复扣费，并能切换或按预案退款。

  7. **小额灰度后再放量**
     - 用有限客户和有限预付池跑真实交易，再逐步扩大。
     - **验证：**完成一次真实周期对账、一次上游故障演练、一次未消费余额退款或迁移演练后，才视为达到上线条件。

  ## 其他人可能漏掉的重叠点和风险

  - **“全自动”“不控制伙伴服务器”“只有 Session 管理接口”三者存在硬冲突。**B 只消除了逐客开户依赖，不会自动获得企业付款、充值码生成或余额调平能力。
  - **客户充值款不宜理解成“过手后拆一笔给伙伴”。**更干净的交易结构是自己向客户零售、再向伙伴批发采购；这也能减少代收代付、支付“二清”、发票和税务处理上的歧义，具体仍应让法务和会计确认。
  - **现有三层幂等和 EA 的 HMAC 不等于 AI 计费全链路幂等。**上游重试、支付回调、流式响应中断和本地账本提交都需要独立的去重与状态机。
  - **按次零售价与按 token 成本之间可能出现负毛利。**深度模式、长上下文、高倍率模型和自动故障转移都会放大这一问题，不能只看平均毛利。
  - **聚合 token 只隐藏客户身份，不隐藏提示词内容。**交易账号、持仓和个人信息可能沿伙伴继续流向实际模型提供方，需要全链路日志与数据使用约定。
  - **客户端中的任何 token 都可能被提取。**B 的价值是即使 `nk1.*` 泄露，也不会泄露伙伴主 key；仍需令牌吊销、轮换、权限范围、限速和异常用量检测。
  - **备用上游不是单纯技术开关。**切换可能改变模型质量、成本、数据去向和服务条款，必须有允许切换的模型清单、价格上限和客户告知规则。
  - **伙伴跑路时最大的风险往往不是停用，而是“客户余额负债 + 不可退预付额度”同时留在自己账上。**预付敞口和退款准备应与扩张速度联动，而不是等事故后处理。
