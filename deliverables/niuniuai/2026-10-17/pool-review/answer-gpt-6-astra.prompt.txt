# BRIEF：牛牛AI 上游号池合作模式的自动化架构

## 一、背景

产品：牛牛AI v1 —— Windows 桌面交易助手（Electron 25 + 自研 MQL5 EA 桥接 MT5）。已有付费客户。

已建成资产：
- Electron 客户端 + 自研 EA（MT5 文件 IPC + HMAC-SHA256 命令签名 + 三层幂等）
- 自建 AI 网关 `ai-gateway/`（零依赖 Node 22）：`/v1/chat`（OpenAI 兼容）、`/v1/credits`、`/v1/admin/{topup,token,ledger}`
- 计费：预扣 → 结算多退 → 失败全退；快问 1 积分、深度 6 积分，1 积分 = ¥0.1
- 客户端已有 AI 积分条（余额展示 + 充值入口 + 绑定令牌）
- 授权：Ed25519 离线验签，客户拿授权码激活客户端

## 二、新增需求（需求方原话转述）

不做自建上游，改为「号池合作」：
1. 找一个信得过的伙伴，由他提供上游 token 服务（对方手上是 New API / One API 类中转站，即所谓的"号池"）
2. 我的客户在 niuniuai.app 注册新账户后，**伙伴那边的号池自动为该客户建立一个 API token**
3. 客户充值的钱经过我的网关，**扣掉我的利润后，自动充值到伙伴的中转站账户**
4. 全流程自动化，不要人工操作

## 三、已核实的事实（2026-10-17 实际查证，非推测）

New API（QuantumNous，GitHub 19.2K star）实际接口能力：
- `POST /api/user/` — 管理员创建用户（role=1 普通用户）
- `POST /api/token/` — 创建令牌，响应直接返回完整 key，无需再查询
- `POST /api/redemption/` — 管理员批量生成充值码（单次上限 100 个）
- `POST /api/user/topup` — 用户侧兑换充值码（注意：是**兑换码**机制，不是直接给余额加钱的管理接口）
- 认证方式：**除 relay 接口外，管理接口全部是 Session 鉴权**（web 登录 cookie），没有官方开放的管理 API Token
- 官方文档明确：Quota 单位 1 USD = 500,000 quota；三级倍率 = 模型倍率 × 分组倍率 × 补全倍率；分组倍率可为不同用户组设不同计费系数（如 enterprise-client: 0.8）
- 有实测改造文章指出：New API「设计重心是人工操作的管理界面，对纯 API 驱动的自动化场景支持不足」，需要自己改 Go 源码补管理端点（即"最后一公里"问题）

## 四、我看到的分叉

**方案 A：客户直连伙伴（我只做收银台 + 账号中心 + 授权中心）**
- 客户拿伙伴发的 token，客户端 baseURL 指向伙伴
- 优点：我不扛推理流量成本与稳定性责任
- 风险：客户能看到伙伴地址与 token → 可能绕过我直接续费；伙伴完整掌握我的客户名单；客户端要改成可配置 baseURL

**方案 B：客户永远只连我的网关（伙伴只做"批发"）**
- 客户只有我签发的 `nk1.*` token，对上游一无所知
- 我持有少量伙伴 token，网关转发
- 分账 = 按用量定期结算给伙伴
- 代价：流量与稳定性责任在我；需要多上游故障转移

**方案 C：混合 —— 伙伴按人头开子账户用于对账，但流量仍过我**
- 每客户一个上游 token，仅用于「按客户统计用量」与「按客户充值」
- 复杂度最高

## 五、请逐条回答的问题

1. 三个方案你怎么选，为什么？如果选 B，"每个客户一个上游 token"是否完全没有必要？如果选 A，我的护城河还剩什么？有没有我漏掉的第四方案？

2. 若确实需要自动化开子账户：New API 只有 Session 鉴权。三条路 —— (a) fork 改 Go 源码加管理端点，(b) 脚本模拟登录拿 cookie，(c) 管理端批量生成充值码 + 客户自助兑换。在**我不控制伙伴服务器**的前提下哪条可行？如果伙伴不愿意改源码，是不是就只剩方案 B？(b) 的安全性代价具体是什么？

3. 分账时机：每笔调用实时分账 vs 按周期（日/周）批量结算。各自的失败模式与对账成本？「我扣掉利润后把余额打给伙伴」在实时模式下每笔要调多少次伙伴接口？有没有必要做一个"虚拟子账本"再定期调平？

4. 伙伴跑路 / 限流 / 账号被封 时，我这边怎么保护已付费客户？需要什么前置约定（预付额度上限、多伙伴兜底、余额隔离、SLA）？

5. 怎么让伙伴**看不到或者不在乎**我的客户名单？技术上（子渠道标识、聚合账号、用量混淆）和商务上（合同条款）分别怎么做？

6. 毛利怎么加最干净？用上游的「分组倍率」加价，还是保留我自己网关的积分定价？两者叠加会不会重复计费或者让对账变复杂？

7. 请给出一个**最小可上线的实现清单**（按依赖排序，标明每步的验证方式），并指出哪一步是必须先跟伙伴谈定的商务前置、谈不拢就不能写代码。
