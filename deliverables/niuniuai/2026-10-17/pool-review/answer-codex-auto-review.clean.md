1. 【结论】优先选 B；不要把“每客户一个上游 token”作为默认设计。A 只适合验证市场，C 只有在伙伴提供稳定的客户级统计/充值能力时才有意义。

【理由】B 保留客户关系、定价权和数据控制权，伙伴只是批发上游。每客户一个上游 token 并不能天然带来更好的对账，反而增加开通、泄露、回收、同步和故障处理成本。A 的护城河只剩客户端、品牌、授权体系、积分计费、交易功能和客户服务；若 AI 能力是核心卖点，伙伴地址和 token 暴露后，客户容易绕过你。

【具体做法】

- 客户只拿 `nk1.*` 网关 token，客户端固定连接你的网关。
- 网关维护客户积分、用量、退款和审计账本。
- 上游采用批发账号或少量隔离账号，不向客户暴露。
- 上游按模型、倍率、时间窗口和客户群统计用量，定期对账。
- 若要客户级追踪，使用你自己的内部 customer_id，不要求上游为每个客户开账号。
- 第四方案是“托管批发适配层”：伙伴继续使用 New API，但由伙伴提供稳定的专用批发接口、账单导出、余额查询、充值/结算接口和 SLA；你只对接这层。它比直接 fork 或模拟后台更适合长期合作。
- 也可以采用“预付资金池 + 你方虚拟子账本 + 周期结算”的 B 增强版，而不是 C。

2. 【结论】在不控制伙伴服务器的情况下，三条路中只有 (b) 和 (c) 可以立即实施；长期可运营性上，最好要求伙伴提供正式接口。伙伴不愿改源码且不提供可靠批量账单能力时，应退回 B，而不是强行做 C。

【理由】(a) 需要伙伴接受部署、升级和安全维护，你无法单方面完成。(b) 虽然可行，但依赖后台页面、Cookie、CSRF、字段和版本，属于脆弱的逆向集成。(c) 可绕过“直接充值余额”的限制，但兑换码存在库存、分配、泄露、重复兑换、过期和对账问题，且仍需要解决自动创建用户/token 的问题。

【具体做法】

- (a)：只有伙伴明确授权、共同维护 fork、约定升级责任，并提供专用管理端点时才采用。
- (b)：仅作为短期过渡；独立专用管理员账号、IP 白名单、最小权限、短期 Cookie、密钥托管、登录失败熔断、请求审计、页面/API 变更监控和人工紧急撤销都必须具备。
- (c)：由伙伴预生成充值码批次，你方保存批次号、面值、状态和兑换客户；兑换成功后记录上游用户、金额、时间和幂等键。充值码必须一次性、短有效期、分批小额发放。
- 若伙伴不改源码，也不愿提供稳定的批量接口、账单导出或安全授权方式，C 不应上线；B 可以先上线，但必须以“批发账户余额 + 你方账本”运行。

(b) 的具体安全代价包括：Cookie 相当于后台会话凭证，泄露后可能获得全局管理员能力；无法像 API key 一样精确限定权限和吊销单个操作；登录流程、验证码、2FA、CSRF 和页面改版会导致自动化中断；异常重试可能重复创建用户、token 或充值；审计上也较难证明每次管理动作的授权边界。

3. 【结论】采用“调用实时记账、资金周期结算”。不要每笔调用都向伙伴转账，也不要把伙伴接口放进用户请求的关键路径。

【理由】实时分账会把上游延迟、失败、重复扣款和网络抖动直接传导给客户请求；每笔调用至少需要一次用量确认或扣款操作，若还要充值，往往涉及扣减、充值、确认、重试等多次交互。周期结算虽然有信用暴露和期末对账成本，但可以批量处理、容错和人工复核。

【具体做法】

- 每次请求在你方完成：预扣积分、生成 request_id、记录模型/输入输出 token、上游成本估算、结算和退款。
- 不实时向伙伴扣款，只维护客户账本、伙伴虚拟应付账本和资金池余额。
- 日级生成对账快照，周级或约定阈值触发结算。
- 结算前锁定账期，生成不可变账单；付款后记录交易号和确认结果。
- 同时保存三组数字：客户实际消费、上游实际消费、你的应付金额。
- 设定资金池低水位和高水位：低于低水位暂停高成本模型或切换备用伙伴，高于高水位才批量补充。
- 虚拟子账本有必要，但它是内部会计层，不应被误认为伙伴真实余额。定期调平时允许设定容差，差异进入异常队列，不能静默抹平。

4. 【结论】把伙伴视为单点故障和信用风险处理。上线前必须建立可切换的上游、隔离资金和客户补偿机制；只靠口头承诺或伙伴“信得过”不够。

【理由】伙伴跑路、限流、封号时，客户已经付费，你仍承担交付责任。若所有客户余额都对应伙伴账户，伙伴余额被锁定会同时造成服务和资金双重损失。

【具体做法】

- 预付额度设上限，按预计 3—7 天消耗控制，而不是一次性存入大额资金。
- 客户充值资金与上游预付款在你方账上分离记录，保留未消费客户余额和可退款金额。
- 至少准备一个备用上游，接口协议统一为内部 provider adapter。
- 备用切换按错误率、延迟、余额、限流和封禁信号自动触发，并支持人工强制切换。
- 对高成本模型设置单客户、单日、单小时限额。
- 约定 SLA：可用性、限流阈值、余额告警时效、故障通知、恢复时间、数据导出、退款责任和封号处理。
- 约定预付余额的所有权、冻结时的退款/返还期限、争议期间可抵扣金额。
- 保留一部分现金或信用额度用于紧急切换，不把全部流动性压在伙伴处。
- 本地客户账本必须可独立导出；即使伙伴不可用，也能准确计算客户应退金额。

5. 【结论】技术上不能保证伙伴永远不知道客户名单，只能做到“伙伴看不到真实身份、也不需要知道客户关系”。最有效的是聚合账号 + 你方内部账本，而不是依赖简单混淆。

【理由】若伙伴为每个客户创建真实用户或 token，伙伴天然能看到规模、注册节奏和客户标识。子渠道标识、随机 ID 和用量混淆只能降低可读性，不能消除关联风险。

【具体做法】

技术上：

- 使用一个或少量批发账号承载请求，不传客户邮箱、手机号、姓名等 PII。
- 只向上游传随机化的 tenant/request 标识，例如不可逆映射的 `partner_subject_id`。
- 日志、Referer、客户端配置和错误信息中不得暴露真实客户身份。
- 客户级账单、积分和风控全部在你方完成。
- 如必须客户级上游统计，使用虚拟租户 ID，并按时间窗口批量汇总，避免实时暴露客户行为。
- 不要通过制造虚假流量或错误用量来“混淆”账单，这会破坏审计并可能违反合作协议。

商务上：

- 合同明确客户归属、禁止直接营销、禁止绕过你收款、禁止导出或复用客户数据。
- 约定数据最小化、用途限定、保密、删除期限、违约赔偿和离职/终止后的数据返还。
- 约定伙伴只能看到其履约所必需的批发数据。
- 规定伙伴不得基于流量模式推断并接触你的终端客户；但不要把技术上无法保证的“完全不可识别”写成绝对承诺。

6. 【结论】保留你自己的积分定价作为唯一客户计费层；上游分组倍率只作为成本控制或批发折扣，不要把两套加价逻辑同时暴露给客户。

【理由】客户只应看到稳定、可解释的积分价格。若你同时提高积分价格、又提高上游分组倍率，容易重复加价；若两边倍率都参与结算，模型倍率、分组倍率、补全倍率的组合会让毛利和账单难以解释。

【具体做法】

- 客户侧固定：快问 1 积分、深度 6 积分，或由你定义明确的模型价格表。
- 你方内部保存每个模型的上游成本、预估成本和实际成本。
- 优先向伙伴争取 enterprise/批发组折扣，把它视为降低采购成本，不作为客户加价接口。
- 若必须使用上游分组倍率，建立唯一的成本换算公式，并在内部账单中保留原始 quota、模型倍率、分组倍率和补全倍率。
- 客户扣积分只发生一次；上游产生的 quota 只用于成本核算，不能再次扣客户积分。
- 毛利计算统一为：客户实际消费收入 − 上游实际成本 − 支付/退款/故障准备金。
- 对预扣、失败全退、多退和模型切换，使用同一套 request_id 和账务流水。

7. 【结论】最小可上线版本应先做 B 的单上游、批发余额、内部账本和可人工切换架构；“每客户上游 token”不是上线前置条件。真正不能绕过的前置是伙伴的接口、价格、结算、故障和数据边界协议。

【具体做法】

1. 先谈并书面确认合作边界。  
   结论：这是必须先谈定的商务前置。  
   内容：批发价格与倍率、计费口径、充值/结算方式、账单导出、余额查询、限流、SLA、故障退款、封号处理、数据使用、客户归属、禁止绕过、终止迁移。  
   验证：双方签署协议，并拿到测试环境或测试账号。

2. 确认伙伴接入能力。  
   结论：优先要求专用批发账号、稳定 relay 接口、账单/余额查询和可导出的用量数据。  
   验证：测试创建请求、查询余额、查询用量、错误码、限流和超时行为。  
   若只能后台 Cookie 自动化，先做风险评估，不作为长期架构。

3. 抽象内部上游适配器。  
   结论：定义统一的 `chat / health / usage / balance / settlement` 接口。  
   验证：用 mock provider 跑完整请求、超时、重试、重复请求和切换测试。

4. 接入你的网关账务。  
   结论：保留现有预扣、结算多退、失败全退和幂等机制，新增上游成本流水。  
   验证：快问、深度、超时、部分响应、上游 5xx、客户端重试和重复 request_id 测试。

5. 建立虚拟资金池与对账账本。  
   结论：客户账本、上游成本账本、伙伴应付账本三者分离。  
   验证：构造充值、消费、退款、汇率/倍率变化和账期关闭场景，确保借贷平衡。

6. 做密钥和资金安全。  
   结论：伙伴凭证只存在服务端密钥存储中，不能进入 Electron 客户端；设置轮换、权限、审计和告警。  
   验证：检查打包产物、日志、异常堆栈和数据库导出，确认没有上游 token 泄露。

7. 增加限流、配额和熔断。  
   结论：先保护资金和上游额度，再追求吞吐。  
   验证：压测单客户、全局并发、余额不足、伙伴限流和恢复场景。

8. 做备用上游和降级策略。  
   结论：至少实现 provider adapter、人工切换和“暂停高成本模型/允许退款”的降级路径。  
   验证：在演练环境人为注入超时、封禁、余额不足和错误率升高，检查客户是否能获得明确结果。

9. 做灰度上线。  
   结论：先内部账号和少量真实客户，设置每日采购上限和自动停机阈值。  
   验证：连续观察账单、毛利、延迟、失败率和差异账，至少覆盖一个完整结算周期。

10. 再评估 C。  
    结论：只有当存在明确的客户级结算、客户级限额、渠道分润或责任隔离需求，且伙伴能提供可靠子账户能力时，才增加每客户上游 token。  
    验证：用实际账期数据证明客户级 token 能解决现有问题，并且新增运维成本低于收益。

「其他人可能漏掉的重叠点和风险」

- New API 的管理接口是 Session 鉴权，不等于“没有 API 就不能自动化”；但模拟后台本质上是在依赖未承诺的内部接口，长期稳定性和责任归属必须单独计价。
- “自动为客户建 token”与“客户流量经过你的网关”是两套互相重叠的身份体系。若没有真实的客户级上游计费或权限需求，C 只会制造双重账户、双重吊销和双重对账。
- 充值码模式可能导致资金先进入伙伴系统，再由你方客户账本解释，形成余额所有权、退款和失效责任的不一致。
- 上游 quota、模型倍率、分组倍率、补全倍率与客户积分不是同一计量单位，必须保存原始量和换算过程，否则毛利无法审计。
- 上游 token、后台 Cookie、客户积分余额、授权码和 HMAC 密钥的泄露后果不同，不能用同一种密钥管理和轮换策略。
- Electron 客户端即使隐藏了配置，也不能被视为可信环境；客户可以逆向、抓包或修改客户端，因此真正的计费、授权和上游保护必须在服务端。
- “多伙伴兜底”如果没有统一模型路由、价格归一化、上下文限制和错误语义，切换后可能出现隐性超额成本或回答行为变化。
- 客户付费余额和伙伴预付款不能简单一一对应；必须明确客户未消费余额、已预扣余额、上游沉淀余额和可退款余额分别属于哪一方。
- 伙伴知道你的总量、模型结构和高峰时段，即使不知道客户姓名，也可能推断你的商业规模；商务保密条款应覆盖经营数据，不只覆盖个人信息。
- “先跑 B、规模起来再谈 C”总体是稳妥路径，但前提是从第一天就保留 customer_id、request_id、用量流水和 provider adapter；否则未来切 C 会变成重做账务，而不是增加一个上游 token 字段。
- 方案 A 还存在品牌、客户支持、合规和供应商依赖风险：客户遇到上游拒答、数据保留或封号问题，通常仍会找你，而不是伙伴。
