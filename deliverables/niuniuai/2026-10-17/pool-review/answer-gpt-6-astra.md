**判断前提：以下以 brief 中已核实的接口能力为准。New API 的能力不能直接视为伙伴实际部署版本的能力。**

## 1. 架构选择

**【结论】优先 B；按需增加上游分户能力，不把“每客户一个上游 token”设为注册前提。**

**理由：**

你已有网关、积分计费和客户端令牌，B 最能复用现有资产，也便于更换伙伴。真正要挑战的是：**客户注册、客户充值、上游采购，是三个独立业务事件，没有必要逐一同步到伙伴。**

每客户一个上游 token 并非完全无用，它可以支持独立限额、撤销、成本归属和争议举证。但要区分：

- **token 分离**：通常只是访问凭证和统计维度，不能默认余额也隔离。
- **账户分离**：才可能形成独立余额、用户组和账单。
- **本地客户账本**：足以承担你的客户计费，不依赖上游分户。

A 的护城河仍然可以是交易工作流、EA 集成、授权、服务与效果，而非推理转售。但上游凭证进入客户设备后，无法靠技术可靠阻止客户绕开你。A 也不会消除客户对你的稳定性预期，只是减少你承载的流量。

**具体做法：**

先用 B，以本地客户 ID、请求 ID、价格版本记录消费；上游采用少量按环境、业务或风险池划分的 token。

第四方案可考虑 **BYOK：客户自行购买推理服务，你收软件订阅与服务费**。它避免上游充值和分账，但会改变目前积分商业模式，适合企业客户或高级套餐。

C 只有在伙伴确实支持分户报表、限额或结算，并能解决明确问题时才值得引入。不要仅为了“未来可能对账”提前建设。

## 2. 不控制伙伴服务器时如何自动化

**【结论】三条路均有前提；伙伴不改源码，不等于只能选 B。但现有接口清单不足以证明可以实现完整、可靠的无人值守分户流程。**

**理由与具体做法：**

| 路径 | 可行条件 | 建议 |
|---|---|---|
| a. fork 增加管理端点 | 伙伴愿意部署、维护和承担升级适配 | 你单方面写 fork 无法解决生产部署；先取得伙伴承诺 |
| b. 登录获取 cookie | 伙伴授权自动化，登录流程允许机器执行 | 可作为受限过渡方案，不能把普通后台登录当成稳定服务接口 |
| c. 生成充值码、客户兑换 | 客户愿意完成兑换 | 只能解决充值的一部分，不能自动完成开户和令牌交付，也不符合全自动要求 |

还需验证一个容易遗漏的环节：**管理员创建用户之后，怎样以该用户身份创建 token？** 已知 `POST /api/token/` 能返回 key，不代表管理员能指定任意用户作为 token 所有者。用户兑换充值码也存在同样的身份切换问题。

b 的具体代价包括：

- 保存后台密码、会话 cookie，泄露后可能获得远超推理调用的权限。
- 会话过期、验证码、双因素认证、登录风控和后台升级都可能中断任务。
- 超时后无法判断创建是否成功，重试可能重复开户、发码或入账。
- 如果需要代客户登录，还要管理更多身份凭证和会话。

若使用 b，应由专用后台任务执行，凭证隔离、限制网络来源、操作审计；先确认结果再重试，遇到无法确认的状态进入异常队列。**不允许通过关闭认证保护来满足自动化。**

伙伴不改核心源码，也可由其提供独立适配服务或现成代理商接口；这仍然需要伙伴配合。A 同样可以让客户自行开户，因此“只有 B”并不成立；但若要求自动化且复用现有体验，B 最现实。

## 3. 分账时机与账本

**【结论】客户消费实时记账，上游按实际成本日对账、按额度或周期结算。必须有本地账本，但不必复制一套上游客户余额。**

**理由：**

“充值扣利润后转给伙伴”混合了零售收款与采购结算。客户尚未消费时，你不知道最终模型、输入输出长度、失败率和采购成本，不能把固定扣款后的余额直接当成上游应得金额。

若双方明确约定收入分成，则可以按约定比例计算，但这与按推理用量批发是两种不同合同。

| 方式 | 主要失败模式 | 对账成本 |
|---|---|---|
| 每次调用同步分账 | 推理成功但结算失败、超时重试重复扣款、伙伴账务故障拖垮推理 | 每笔都要处理跨系统不一致 |
| 周期批量结算 | 未结敞口增长、延迟发现价格差异、账单缺漏 | 仍需请求级明细，但资金操作和故障补偿较少 |

**具体做法：**

记录至少四类业务：客户充值、积分预扣与结算、上游实际或暂估成本、供应商付款及额度变动。调整使用冲正记录，不覆盖历史。

每笔充值需要多少次伙伴接口，取决于路径：

- 已有用户且会话有效，按充值码实现入账，至少是**生成充值码一次＋用户兑换一次**。
- 另可能需要登录、查询结果、余额核验及异常恢复。
- **实际付款给伙伴是另一条资金链路**；上述两次接口不能证明钱已付给伙伴。
- B 使用已有采购额度时，每次推理通常只需 relay 请求，无须附加一次“分账调用”；用量核验可以异步完成。

采用日对账、小额滚动补款或有限授信。保留差额阈值、未知状态队列和人工异常处理通道。“全自动”应指正常路径自动完成，不应承诺异常永远无需处理。

## 4. 伙伴故障时如何保护已付费客户

**【结论】客户积分债务由你承担，不能随伙伴余额一起消失。保护核心是控制采购敞口、保留履约资金与验证过的替代供应。**

**理由：**

客户钱全部提前转给伙伴，即使本地积分还在，伙伴跑路后你也可能没有资金继续履约。“余额隔离”首先是账务与资金安排，不是数据库中多一个字段。

**具体做法：**

上线前谈定并落实：

- **预付上限**：依据近期采购消耗和可承担损失设置，禁止无限自动补款。
- **退款与退出**：未消耗采购额度如何退、终止服务提前多久通知、账单如何导出。
- **价格与限流**：价格调整通知期、并发和速率上限、模型变更规则。
- **SLA**：故障响应、恢复目标、异常扣费处理；赔付条款不能替代实际备用能力。
- **备用上游**：验证接口、模型行为、成本和数据处理条件；两个伙伴若共用同一底层号池，未必能真正容灾。
- **本地保护**：熔断、排队上限、暂停销售、失败退款和状态提示。

在未拿到有效结果前不要自动无限重试。客户端超时不等于上游没有执行，盲目切换可能产生双重成本。

涉及 EA 的操作必须继续经过既有签名和幂等校验，故障转移不能触发重复交易指令。

## 5. 客户名单保护

**【结论】B 可以减少伙伴获得直接客户身份的机会，但无法保证伙伴不知道终端客户的存在。商务上要让伙伴的收益来自你的规模采购。**

**理由：**

聚合 token 隐藏了账户列表，但提示词、交易日志、账户号码、请求时间和业务特征仍可能泄露身份。C 的稳定客户标识还可能让伙伴长期关联同一客户。

**具体做法：**

技术上：

- 注册邮箱、手机号、付款信息和软件授权身份留在本地。
- 移除不必要的客户标识、原始 IP 转发和设备信息。
- 需要分户时使用随机、不含身份信息的标识，本地保存映射。
- 对提示词、附件和日志中的非必要身份字段脱敏。
- 不做虚假调用或“用量混淆”：增加成本，也不能形成可靠隐私保证。

商务上：

- 约定客户数据用途、保留时间、删除机制和日志访问权限。
- 约定不得利用服务数据定向招揽你的客户。
- 通过聚合采购量、稳定结算和明确支持边界，使伙伴服务你的收益高于逐个争取客户。

合同能够约束行为，不能代替数据最小化。

## 6. 毛利与价格

**【结论】保留自己的积分定价；伙伴分组倍率只作为采购价格参数。**

**理由：**

你的客户购买的是产品服务，不需要理解 quota、美元价格和模型倍率。上游分组倍率由伙伴控制，不适合成为你的零售价格权威。

两层价格本身不会重复收费：客户向你买服务，你向伙伴买推理，是两次不同交易。真正的问题是**同一客户请求既扣本地积分，又要求客户自己支付上游余额**，或把采购倍率重复套入成本计算。

**具体做法：**

每笔请求保存：

- 零售积分扣减、折扣和价格版本。
- 上游供应商、实际模型、用量、价格版本。
- 实际扣除 quota、对应采购成本及换算口径。

`1 USD = 500,000 quota` 是名义单位定义，不自动等于你的实际人民币采购成本；折扣、赠送额度和结算汇率应单独记录。

快问 1 积分、深度 6 积分是固定售价，需要控制输入长度、最大输出、工具调用次数和重试预算，按真实成本分布检查毛利。不要只看平均请求成本。

## 7. 最小可上线清单

**【结论】先确定交易与结算合同，再沿用现有网关上线 B。新增部分集中在上游适配、采购账本、支付幂等和故障保护。**

| 顺序 | 实现内容 | 验证方式 |
|---|---|---|
| **0. 商务前置** | 确认允许转售、采购价格、付款及额度来源、明细核验方式、预付上限、退出退款、数据用途与限流规则 | 双方书面确认；小额验证付款、额度到账、调用扣费和账单一致 |
| 1. 固化业务边界 | 明确客户积分独立于上游余额；定义失败退款、超时待核验和价格变更规则 | 用注册、充值、调用、退款及停服场景逐一走查 |
| 2. 完成身份映射 | 网站账户关联本地客户、网关令牌和软件授权；上游凭证仅留服务端 | 测试重复注册、令牌撤销、跨账户访问和激活绑定 |
| 3. 加上游适配 | 配置伙伴地址、密钥、模型映射、超时及限流 | 用真实流式与非流式调用验证响应、用量和错误行为 |
| 4. 补采购账本 | 复用已有积分账本，新增成本、供应商额度及付款记录 | 验证重复请求、进程重启、迟到结果和冲正后账目一致 |
| 5. 接支付与自动补款 | 验签、订单幂等、到账后积分入账；采购补款独立处理 | 重放、乱序、延迟回调及付款结果未知测试，确保不重复入账或付款 |
| 6. 做核对与告警 | 每日比对本地请求成本、伙伴账单及额度变动 | 构造漏单、重复扣费和价格差异，确认可发现并定位 |
| 7. 做故障保护 | 熔断、额度阈值、停售开关、失败退款；若承诺连续服务则接入备用伙伴 | 注入超时、429、余额不足和封禁，核验客户余额及重复执行风险 |
| 8. 小流量放量 | 限客户数、单日采购额与最大输出 | 完成一个真实结算周期，确认账平和毛利后扩大 |

**第 0 步谈不拢，不应开始面向该伙伴的生产集成。** 尤其是“实际付款怎样自动换成可调用额度”，不是拿到 relay token 就自然解决了。

若伙伴既没有自动到账通道，也不提供可接受的授信或额度安排，**B 能解决推理接入，但仍然无法满足采购全自动**。这是需要明确承认的业务阻塞。

## 其他人可能漏掉的重叠点和风险

- **充值码不等于资金结算。** 发码和兑换只是平台记账动作，必须明确对应谁的已付款、授信或负债，否则可能形成无资金支持的额度。
- **需求中的“每客户一个 token”可能只是实现想象。** 应保留的是客户可独立计费、可追踪、可撤销的能力，而非特定上游凭证形态。
- **退款风险与采购预付叠加。** 客户退款或支付撤销时，上游成本可能已发生；全部自动转出会扩大现金缺口。
- **失败全退不等于成本全退。** 上游已经生成但客户端未收到结果时，你可能承担采购成本。需独立核验，不能把本地退款当作供应商退款。
- **“B 以后升级 C”并非天然成长路线。** C 应由独立限额、合同分户或审计需求触发；规模增长本身不构成理由。
- **自动故障转移会影响交易语义。** 同名模型可能表现不同，不能为了可用率静默替换成未经验证的模型，再直接影响交易操作。
- **软件授权与消费身份要统一关联、分开控制。** 离线授权通过不代表网关调用仍然有效；积分账户停用也不必自动使整个客户端失效。
- **幂等不等于端到端恰好一次。** 你现有三层幂等能保护本地流程和 EA，但如果伙伴不支持幂等请求与结果查询，就仍然存在上游重复执行和未知扣费窗口。
