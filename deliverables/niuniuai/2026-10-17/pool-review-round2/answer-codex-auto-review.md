## 一、技术方案

### 1. 结论：更正会强化方案 B，但不会自动证明方案 B 适合生产。

理由：官方 Access Token 解决了密码、模拟登录和长期 Session 的问题，管理员操作也更容易审计、撤销和限制来源 IP。但 Admin 令牌仍可能拥有批量开户、改额度、读用户信息甚至创建令牌的高权限，一旦泄露，影响范围很大。

具体做法：

- 优先让伙伴提供专门的经销商 API 或独立租户，而不是直接交生产环境 Admin Token。
- 如果只能使用 Admin Token，必须建立独立的代理租户、独立密钥、独立 IP 白名单和独立审计日志。
- 不在客户端软件中保存令牌，只放在服务端密钥系统中。
- 上线前先验证接口权限、撤销机制、日志内容、限流和故障恢复能力。
- 方案 B 还必须以“上游来源合规、允许转售”为前提；技术可行不等于商业或法律可行。

### 2. 结论：每客户一个上游 token 通常仍然不必要，但每客户一个逻辑子账户或租户隔离值得考虑。

理由：为每个客户创建真实上游 Token，会增加密钥泄露、轮换、回收、配额同步和上游封禁的复杂度，也可能违反上游禁止共享或转售的条款。真正有价值的是内部隔离，而不是把每个客户都变成上游账号。

具体做法：

- 默认采用“你的后端持有少量上游凭证，内部按客户隔离”的模式。
- 每个客户建立内部 tenant_id、额度、调用日志、限流、退款和封禁状态。
- 只有在以下场景才考虑每客户独立上游子账户：上游合同明确允许、客户需要独立审计或账单、隔离故障很重要，且上游有正式的子账户机制。
- 不要批量注册大量“看起来像个人用户”的账号来规避风控或转售订阅。

### 3. 结论：受限 Admin 令牌应收口到“最小业务能力”，并默认不允许管理令牌和系统配置。

理由：Admin 令牌的风险不只在额度修改，还包括横向读取用户、创建新令牌、访问敏感数据、修改模型渠道和影响整个实例。若平台不能提供细粒度权限，Admin 令牌本身就不适合作为长期生产凭证。

具体做法：

能做：

- 仅创建、停用和查询你名下的代理子账户。
- 仅修改你名下客户的额度。
- 查询必要的用量、余额和调用状态。
- 使用固定的业务接口，不允许任意 URL 转发。

不能做：

- 读取伙伴其他客户数据。
- 创建或导出任意系统 Token。
- 修改 Root/Admin、模型渠道、系统配置、支付、日志保留和安全策略。
- 删除审计日志或修改历史账单。
- 访问原始提示词、客户文件或不必要的个人信息。

防滥用：

- 使用专用账号和专用令牌，不使用伙伴个人账号。
- IP 白名单、服务端密钥托管、短周期轮换、立即撤销能力。
- API 网关限制方法、路径、参数、频率和额度。
- 所有开户、调额、停用操作写入不可篡改审计日志。
- 设置单客户、单日、全局额度上限和异常告警。
- 令牌泄露、伙伴关系终止或异常调用时自动熔断。
- 若无法实现以上限制，应改为由伙伴侧执行开户和调额，你只调用普通业务接口。

## 二、合规风险

### 4. 结论：如果上游属于灰色号池，你可能承担合同违约、民事赔偿、行政处罚、平台封禁，严重时还可能面临刑事风险；“我不知道”通常不是可靠抗辩。

理由：下游把服务包装、收费并提供给境内客户，通常不是被动使用者，而是经营链条中的实际服务提供方。若存在明显低价、批量账号、境外身份借用、免费额度套利、封号退款套利或绕过平台限制等迹象，继续采购可能被认定为明知或应知。是否构成犯罪必须结合主观故意、交易规模、获利、技术行为和具体罪名判断，不能仅凭“不知道”排除风险。

具体做法：

- 对上游来源、授权、账号取得方式、模型服务条款和转售权进行书面尽调。
- 保存合同、发票、付款记录、授权链、审计日志和异常处理记录。
- 对明显异常低价、无法说明来源、要求代持身份或规避风控的供应商直接拒绝。
- 发现封号、退款套利、身份冒用或接口被投诉时立即停止采购并保留证据。
- 在律师审查前，不要按“号池”“共享会员”“境外账号池”等模式上线。

### 5. 结论：应索取完整的主体、授权、合规、税务和责任承担文件；单方承诺不足以完全隔离风险，但能显著降低你的证明和追责风险。

理由：隔离的核心是证明你选择了可验证的正规供应商，并且合同明确禁止违法来源、未经授权转售和违规处理个人信息。合同不能免除法定义务，但能帮助证明你没有明知参与，也能提高追偿能力。

具体做法：

至少索取：

- 伙伴营业执照、实际控制人和收款主体信息。
- 上游供应商、模型厂商或一级代理的授权证明。
- 明确允许 API 调用、商业转售、境内客户使用和二次分销的合同条款。
- 模型厂商服务条款、可接受使用政策和限流规则。
- 相关备案、许可、资质或备案编号，以及其适用范围。
- 发票、采购合同、付款链和额度来源证明。
- 数据处理协议，明确提示词、文件、日志和个人信息的存储、处理及跨境情况。
- 安全事件、封禁、投诉和监管调查的通知义务。
- 反贿赂、反欺诈、反洗钱和不得使用盗用账号、借用身份、免费额度套利的承诺。
- 违规时的退款、替代供应、赔偿、配合调查和审计权条款。

### 6. 结论：备案责任不能简单归给模型厂商；你是否需要自行备案，要按你实际提供的服务形态判断，不能因为调用了已备案模型就当然免除。

理由：模型厂商的模型备案或安全评估，通常只覆盖其模型和其提供的服务边界，不当然覆盖你向公众提供的应用、内容生成服务、用户管理、审核和运营责任。你可能同时承担应用运营者、生成式 AI 服务提供者、网络服务经营者和数据处理者的义务。

具体做法：

- 让律师依据你的产品功能、用户范围、部署位置、数据流和收费方式判断是否属于面向公众提供生成式 AI 服务。
- 核查是否涉及算法备案、生成式 AI 服务备案、安全评估、内容审核、个人信息保护、网络安全、ICP 或其他经营资质。
- 在产品中保留用户协议、隐私政策、内容安全规则、投诉举报渠道、日志和人工处置机制。
- 不宣传“官方模型直供”或“已备案所以你无需负责”，除非合同和法律意见明确支持。
- 若仅是企业内部工具、非公众开放、且不保存或处理敏感数据，责任边界可能不同，但仍需书面确认。

### 7. 结论：只接境内正规模型官方 API，且由伙伴做有授权的聚合和批发，风险会显著下降，但不会自动降到可接受。

理由：可以减少盗号、境外账号、共享订阅和灰色号池风险；但仍可能存在无权转售、数据跨境、内容安全、隐私保护、消费者退款、税务、服务连续性和备案责任问题。

具体做法：

- 直接核验模型厂商与伙伴之间的授权链，而非只看伙伴口头说明。
- 合同明确模型名称、接口主体、转售地域、客户类型、数据处理地点和故障责任。
- 尽可能与官方或正式一级代理签约，付款给合同主体并取得发票。
- 通过服务端调用，不让客户接触上游密钥。
- 对提示词、上传文件和输出内容进行最小化留存、权限隔离和安全审计。
- 对内容安全、投诉、退款、停服和模型切换建立预案。
- 正式上线前取得律师对备案、数据和合同链的书面意见。

### 8. 结论：以下形态应直接拒绝；一句话尽调应同时询问来源、授权和转售合规。

理由：这些模式要么具有明显违法或欺诈特征，要么无法形成可审计、可追责的供应链。低价不能抵消刑事、行政、封号和客户赔偿风险。

必须拒绝：

- 借用、购买或批量使用境外个人身份证件完成认证。
- 批量注册账号、领取免费额度后集中转售。
- 共享个人会员、共享密码、共享长期 Session 或绕过设备/地区限制。
- 明知违反模型厂商条款仍进行 API 转售。
- 无法提供真实供应商、授权链、合同或发票。
- 要求你代收客户资金、代做退款套利或故意触发封号。
- 账号来源、额度来源和价格明显异常，且伙伴拒绝解释。
- 使用盗号、撞库、破解、代理绕过、虚假身份或虚假交易取得额度。
- 不能说明数据是否出境、由谁保存、保存多久。
- 要求把高权限 Admin Token 放入客户端或交给不受控的第三方。

尽调话术：

> 为了满足客户审计和我们双方的风险控制，想确认一下：这些额度的合法来源、模型厂商或一级代理授权、是否明确允许境内商业转售，以及能否提供合同、发票和数据处理说明？

## 三、最小可上线路径

结论：最小可行路径应是“正规模型或正式一级代理 + 书面转售授权 + 你的服务端代理层 + 内部客户隔离 + 合规审查后小范围试运行”。

具体做法：

1. 暂停灰色号池、共享订阅、境外身份账号和免费额度套利方案。
2. 选择境内模型厂商或可验证的正式代理。
3. 取得主体资质、授权链、采购合同、发票和数据处理文件。
4. 由你的服务端托管上游密钥，客户端只访问你的业务接口。
5. 建立客户额度、日志、限流、投诉、退款和熔断机制。
6. 先用少量客户做封闭测试，验证停服、封号、超额和数据删除流程。
7. 由律师确认备案、内容安全、隐私、数据跨境、消费者和合同责任。
8. 由会计确认收入确认、发票、税务和代理/转售模式的账务处理。
9. 取得书面意见后再扩大客户范围。

在没有律师或会计意见前，不应执行两步：

- 不应以“号池”或不明来源额度面向境内客户收费上线。
- 不应确定最终收费、开票、代理结算、退款和收入确认模式。

## 其他人可能漏掉的重叠点和风险

- “正式模型”不等于“伙伴有权转售”；模型备案、API 授权和商业分销权是不同问题。
- Admin Token 的权限风险与上游来源合规风险是两条独立风险线，不能因为令牌可审计就证明额度来源合法。
- 你的 Windows 客户端可能暴露接口、设备标识、日志或本地缓存，需防止客户提取上游凭证和批量滥用。
- 提示词、上传文件、聊天记录和支付信息可能构成个人信息或敏感数据，需单独设计留存、删除和跨境规则。
- 模型输出可能引发侵权、虚假信息、违法内容和客户损害责任，必须准备审核、投诉和人工干预机制。
- 供应商突然封号或停服时，你仍需对付费客户承担退款、替代服务和通知义务。
- 合同中的“上游承担全部责任”不能排除监管机关直接向你追责，只能改善事后追偿。
- 低价、匿名收款、个人账户收款、无发票和频繁更换上游主体，都是应提高风险等级的信号。
