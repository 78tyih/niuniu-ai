### 1. 对「选方案 B」的影响

**【结论】更正消除了一个技术障碍，但不足以单独证明 B 是最佳方案。** 如果 B 指「由你管理客户和计费，上游提供批发能力」，我倾向保留；如果 B 必须依赖上游全面开放 Admin 权限，则仍需缩小授权。

**【理由】** Access Token 使自动开户、调额无需保存后台密码，这确实降低了凭证管理成本。但 **Admin Token 的实际权限可能接近管理员账号**，不能仅因形式变成 API 密钥，就认定风险已经大幅下降。“可审计、可限定来源 IP”也需核实具体部署，不能由支持 Access Token 自动推导出来。

**【具体做法】** 将两件事分开决策：

- 技术上：确认部署版本、接口权限、令牌返回方式，验证自动化可行性。
- 商业上：确认采购与转售授权、额度结算规则、停供责任。
- 安全上：优先使用伙伴提供的受限业务接口，不直接接收通用 Admin Token。

### 2. 每客户一个上游 Token／子账户是否值得做

**【结论】变得更容易实现，但仍不应作为首发必选项；Token 与子账户需要分别判断。**

**【理由】** 每客户一个 Token 有助于限流、撤销和费用归因，但不一定拥有独立余额；独立子账户通常隔离更强，也增加开户、余额同步、退款和对账复杂度。两者都不能解决上游来源不合法的问题。

**【具体做法】**

- 首发采用「你的客户账本＋你的服务端代理＋独立的上游业务账户」。
- 需要单独停用、硬额度限制或可核验的客户账单时，再引入每客户 Token。
- 确需独立余额或租户隔离时，才增加子账户。
- Windows 客户端只持有你的登录凭证，所有上游密钥留在服务端；不能靠客户端加密或混淆保证秘密安全。

### 3. 受限 Admin 令牌如何收口

**【结论】首选伙伴侧的窄权限网关；不要把“约定只调用几个接口”当成权限限制。**

**【理由】** Public、User、Admin、Root 是角色层级，不等于支持按接口、字段、客户归属精细授权。如果一个令牌仍能修改其他用户，它就没有实现真正的租户隔离。

**【具体做法】**

| 方面 | 应有约束 |
|---|---|
| 可以做 | 创建归属于你的客户、创建或撤销其 Token、查询自己的用量、在已付款额度内分配预算 |
| 不可以做 | 访问其他客户、提升角色、修改供应商渠道及密钥、调整系统配置、删除审计记录 |
| 额度限制 | 单次上限、每日上限、总授信上限；不能凭调额接口无限制造可消费额度 |
| 接入限制 | 固定服务端出口 IP、短周期轮换、独立业务身份、紧急撤销机制 |
| 操作约束 | 幂等请求、并发控制、客户归属校验、额度变更留痕、异常告警 |

尤其要确认 `quota` 是总额度还是剩余额度、修改是否覆盖原值。直接“读余额再写余额”可能覆盖并发消费或重复充值。**管理额度字段不能替代结算账本。**

### 4. 灰色号池给下游带来的风险，以及“不知情”抗辩

**【结论】不建议将所述灰色号池用于境内付费产品；“不知道货源”不是可靠免责方案。**

**【理由】** 你向客户销售软件内的 AI 服务，会承担自己这一环的责任，包括：

- **合同与消费者责任：** 停供、封号、额度失效、宣传不实引起的退款及赔偿争议。
- **数据与隐私责任：** 提示词、文件、个人信息被传至未披露或缺乏适当安排的供应商，涉及跨境时还需单独评估。
- **服务监管责任：** 面向境内公众提供生成式 AI 能力所对应的内容、安全及相关手续。
- **潜在刑事风险：** 若明知或参与盗用身份、账号入侵、骗补骗退款等行为，或为相关犯罪提供帮助，需要结合具体事实判断。

违反平台订阅条款与构成犯罪不是同一件事；brief 中的拘留报道，也不能证明所有 Token 转售都构成某个罪名。反过来，真实不知情即使对某些要求主观明知的犯罪认定有意义，也不当然免除合同或行政责任。

**【具体做法】** 要求说明采购链路并保留核验记录。异常低价、身份借用、频繁换号、要求隐藏来源、不能提供采购证据，都应触发拒绝或暂停合作。已出现明显异常后继续采购，会削弱“不知情”的可信度。

### 5. 应索要的文件与书面承诺

**【结论】文件只能帮助预防、举证和追偿，不能把你的法定义务转移给伙伴。**

**【理由】** “上游保证合法、出事全赔”无法约束监管机关或客户，也无法确保对方有赔付能力。有效隔离依赖真实供应链、实际控制措施和可执行合同共同成立。

**【具体做法】** 至少取得并核验：

1. **主体材料：** 企业登记信息、签约与收款主体、开票安排。
2. **采购及授权链：** 官方 API 采购合同、订单或账单，以及允许相应聚合、转售或嵌入产品的条款或授权。官方 API 能调用，不代表可以随意分销。
3. **模型与手续材料：** 实际模型、供应商、调用地域、相关备案或登记信息，以及它们与交付服务的对应关系。
4. **来源承诺：** 不使用盗号、借用身份、违规免费额度、订阅拆售、骗退款等来源；更换供应链必须事先通知并获约定批准。
5. **数据处理协议：** 数据用途、保存期限、是否训练、分包商、处理地域、删除机制、事件通知。
6. **服务与退出条款：** 可用性、停供通知、余额退款、迁移支持、审计权、违约赔偿。

敏感采购材料可以脱敏或由律师查验，但不能完全以口头承诺替代。

### 6. 备案责任到底落在谁头上

**【结论】不能仅凭模型厂商已备案，就认定你的软件无需任何手续；也不能笼统断言你必须重复做同一套模型备案。**

**【理由】** 应区分底层生成式 AI 服务备案、调用已备案模型的应用或功能登记，以及可能涉及的算法备案、安全评估等事项。责任取决于实际提供服务的主体、功能与适用要求，并非在你、伙伴、模型厂商中三选一。

面向境内公众的软件，即使收费、需要注册或仅通过 Windows 使用，也不能因此当然排除在公众服务范围之外。

**【具体做法】** 准备一页说明，列明运营主体、用户范围、模型清单、数据流向、内容功能、是否允许公开传播，由熟悉当地实践的律师协助向属地主管部门确认：

- 你的应用是否需要登记及对应办理主体；
- 是否触发其他备案或安全评估；
- 伙伴作为聚合服务方另需承担哪些义务；
- 上线前与上线后分别需要完成哪些事项。

### 7. 仅接境内已备案模型是否可接受

**【结论】风险通常明显降低，是优先路线；但“已备案模型＋聚合商”还不足以直接判定可以上线。**

**【理由】** 品牌名称不等于具体服务合规证明。仍需确认实际调用的是对应的官方服务、采购用途允许你的商业模式、数据处理安排符合要求，以及你自身应用手续是否完成。

**【具体做法】**

- 首发优先直接采购一家正规模型的官方 API，减少供应链层级。
- 使用伙伴时，要求明确模型清单、采购凭证及授权依据。
- 合同禁止暗中切换为账号池、境外线路或其他模型。
- 将你自己的用户协议、隐私告知、内容治理、投诉处理及适用的生成内容标识要求一起纳入上线验收。

### 8. 合规红线与尽调话术

**【结论】拒绝依赖身份冒用、欺诈、未授权资源或隐瞒供应链的上游，不能用价格折扣抵消这些风险。**

**【理由】** 此类来源容易同时造成停供、追责和无法追偿；你也难以向客户兑现服务及数据保护承诺。

**【具体做法】** 对以下形态直接拒绝：

- 盗取账号、密钥，购买泄露凭证，冒用或借用身份认证。
- 通过虚假注册、规避限制等手段获取并转卖免费额度。
- 故意触发封号、虚假退款、拒付或其他骗款玩法。
- 无明确授权，将个人包月订阅拆成商业 API 零售。
- 依赖绕过访问控制、伪造身份或持续规避封禁维持供货。
- 不提供可核验来源，或以“商业秘密”为由拒绝任何独立核验。
- 宣称官方线路，实际使用账号池或私自切换供应商。
- 不说明客户数据去向，擅自留存、训练或二次出售数据。

尽调话术：**“我们上线前要统一做供应商审查，麻烦提供采购来源、商用及分销授权、模型备案或登记信息和数据处理说明，敏感内容可以脱敏，双方后续对账和长期合作也更稳妥。”**

### 9. 最小可上线路径及专业意见前的停止点

**【结论】最小路线是：一家正规官方 API＋你的服务端代理与客户账本＋明确的应用合规手续；先不接灰色号池，也不依赖全面 Admin 授权。**

**【理由】** 这条路线可以同时减少供应链、授权、权限和对账的不确定性。伙伴只有在提供可验证的成本或服务优势时，才值得增加这一层。

**【具体做法】**

1. 用测试账号和合成数据完成内部原型，核验成本、限额与故障行为。
2. 确定供应商及具体模型，核查商业使用与交付方式。
3. 完成服务端凭证保护、用量账本、限额、退款及停供机制。
4. 让律师确认应用登记／备案路径、数据流和合同；让会计确认收入、开票、预收款及退款处理。
5. 完成适用手续后，小范围付费上线，再扩大客户量。

**在取得律师意见前，不应向境内公众正式开放并收费，也不应把真实客户数据交给来源或处理安排未确认的上游。** 内部原型可以先做。

**在会计或税务专业人士确认交易与票据安排前，不宜启动充值余额、长期预付套餐或代收代付模式。** 专业意见不能替代依法必须取得的备案、登记或其他手续。

### 其他人可能漏掉的重叠点和风险

- **可撤销不等于低权限。** Admin Token 撤销前造成的数据访问、额度损失无法自动撤回。
- **三个账本必须区分。** 客户付款、你给客户的可用额度、上游实际结算不是一回事；尤其不能将管理员修改 `quota` 当作采购完成。
- **付款墙不等于非公众服务。** 软件安装、注册和付费并不能当然消除相关监管义务。
- **备案信息必须对应真实线路。** 即使签约时来源正规，后续暗中切换账号池仍会让尽调失效。
- **日志兼具审计价值和泄露风险。** 留存操作人、时间、额度变化及请求编号，避免把完整 Token、提示词和客户文件写入普通日志。
- **追偿权取决于对方是否有偿付能力。** 即便合同完善，也应限制上游预付款规模，并准备可实际切换的备用供应商。
